B1 and B1 + secpatch2 are rescorings, not separate runs. Each takes the episodes of R1 or R2 and scores every continued episode with the patch it held at its first output-limit stop. That is exactly what plain OpenCode submits there, because it exits at a length stop. No other episode changes.

Claim

  • The full harness (continue-on-length + secpatch2) against B1: +8.2 pp pass@1 (66.3% → 74.5%), 95% CI [-0.2, +16.5], p = 0.08. This is suggestive but not significant at 0.05, and it holds on PatchEval val46 only: on held-out nexus tasks the harness showed no gain (section 9).
  • Continue-on-length: +4.9 pp (p = 0.016), the one significant component. Present it as generic agent-loop engineering.
  • secpatch2: +3.3 to +3.8 pp, not significant. Behavioral effects are clearer: the fewest wrong patches (38 against 48), the skill loaded in 184/184 episodes, and 80% of episodes read a weakness-family file.
  • Its cost: the full harness uses +32% input tokens, +22% turns and +30% agent time per episode over B1 + cont.; per solved episode it is +22% at list price ($0.60 → $0.74).

Don't claim

  • The +8.7 pp of Full − B0 (p = 0.023) as a harness gain. It includes the environment fixes.
  • ripgrep, the Python venv, or the id-leak fix. These repair the benchmark environment and belong in every baseline.
  • Full − v1 (+7.6 pp) as "v2 beats v1 by design". v1 never ran in the fixed environment, and its skill tool could not load.
  • Any val46 number as held-out evidence. The secpatch2 method was derived from failures on these 46 CVEs.
  • That the harness generalizes. On 100 held-out nexus cyber-training tasks the full harness scored -1.8 pp against plain OpenCode (95% CI [-4.9, +1.4], p = 0.35), at higher cost (section 9).
Suggested wording. "On PatchEval's 46-CVE validation split (Qwen3.8-27B, 4 samples), our OpenCode harness, with continue-on-length plus a security-patching profile, raises pass@1 from 66.3% for plain OpenCode in the same environment to 74.5% (+8.2 pp, 95% CI [-0.2, +16.5], paired permutation p = 0.08). Continue-on-length alone contributes +4.9 pp (p = 0.016); the security profile adds +3.3 to +3.8 pp (not significant) at +28% cost per episode. On 100 held-out nexus cyber-training tasks the same harness did not help (28.5% vs 30.2%, -1.8 pp, 95% CI [-4.9, +1.4]), mainly because its longer workflow hit nexus's 40-minute agent cap more often."

v1 profile: adapted from codex-security / deepsec

  • Priorities: close the boundary, but also preserve legitimate behavior and compatibility and keep checks passing.
  • A long 7-step workflow with a separate investigation pass, and a review checklist that is read before editing.
  • One large per-CWE reference file (15 kB).
  • Ran only in the original environment, where its skill tool could not load.

secpatch2: rewritten after v1's failure analysis

  • Safe-by-default first: vulnerable behavior is not "legitimate", even when a default or a test asserts it.
  • Short, tool-driven reasoning: plans live in todowrite; an edit is applied as soon as it is known; no recalling upstream fixes.
  • Path inventory and variant matrix before fixing, then a table-driven check of the described impact.
  • Regression triage: narrow the fix, never edit tests. Review only once a diff exists.
  • Benchmark-agnostic: 15 small weakness-family files sized for nexus's 30k context.

  • v1 did not help (+1.1 pp vs B0, not significant). Its skill tool failed in every episode because ripgrep was missing. Its longer guidance produced more output-limit stops (15 against 8), and each of those ends the session with an empty patch.
  • Continuation removed every empty patch. It rescued 9 episodes with the plain profile and 8 with secpatch2, and harmed none.

7. Cost

All four generated runs used the same server (vLLM 0.29.0, 8 × H200, MTP 4, identical argv) and 48 parallel agent containers. Dollar figures apply OpenRouter list prices for Qwen3.8-27B ($0.094 per 1M input, $0.0094 per 1M cached input, $4.4 per 1M output), the same basis as the earlier cost report. They are a common yardstick, not the self-hosted cost; GPU-hours are the self-hosted cost. B1 has no cost of its own because it is a rescoring of B1 + cont.; without continuation, the 13 continued episodes would have stopped early, so B1 costs slightly less.

Reading it

  • Continuation is nearly free. B1 + cont. costs no more per episode than B0 ($0.429 vs $0.438) and is cheaper per solved episode ($0.603 vs $0.666). It continued only 13 of 184 episodes.
  • secpatch2 costs more per episode. Input is +32%, because longer sessions resend the growing context each turn. Output is only +21%. Per solved episode the increase is +22%.
  • Input dominates list-price cost: 64% for the full harness. Output is about 1% of tokens but is priced 47× higher. The prefix cache serves 71% of input, which roughly halves the cost when discounted.
  • Wall-clock and GPU-hours rise less (+9%) than per-episode time (+30%). With 48 parallel containers, a sample ends when its slowest episode does, and samples that include a timed-out episode take 40–47 minutes.

Reading it

  • Rollouts that finish do about as well. Within capped and uncapped rollouts, the full harness is level with or slightly above plain OpenCode. But its longer method (path inventory, variant matrix, checks, review) pushes 15 percentage points more rollouts into the 40-minute cap. The val46 report flagged the same timeout failure mode.
  • Continuation is inert on nexus. nexus reserves 12,288 output tokens in a 30,000-token context, so OpenCode compacts a session once input plus output passes about 17.7k tokens. A response that runs into the output limit always crosses that line. OpenCode then summarizes the session and resumes it with its own "Continue if you have next steps…" message, so the wrapper never sees a session end on a length stop.
  • Compaction is constant in both arms: 399 of 400 rollouts, 17.32 vs 23.43 times per rollout. Unsolved rollouts compact more often. nexus's context and output settings may matter more than the profile; that A/B was not run.
  • Run-to-run noise is about 2 pp. The two full-harness runs scored 30.5% and 28.5%.

Details, per-rollout records and the reproduction scripts are in cyber-train/docs/arthur/qwen38-27b-secpatch2-iid100/ (README, results.json) and cyber-train/scripts/nexus/arthur/secpatch2/. Run 1's raw data was lost when the instance stopped on 2026-10-06; only its summary survives.

10. Caveats

  • Optimistic numbers. The secpatch2 working method was derived from B0 and v1 failures on these same 46 CVEs. The held-out check on 100 nexus tasks (section 9) found no gain (-1.8 pp, p = 0.35). There, both arms got the same ripgrep fallback, consistent with treating ripgrep as an environment fix.
  • Small sample. Per-configuration 95% CIs are about ±10–11 pp. Against B1, only continuation is significant; the full harness is at p = 0.08.
  • Two kinds of contrast. Comparisons between a run and its own rescoring (B1 vs B1 + cont., B1 + secpatch2 vs Full) isolate continuation within the same trajectories. Comparisons between runs (Full vs B1, B1 + secpatch2 vs B1) also carry run-to-run sampling noise.
  • Bundled profile changes. secpatch2 changes the rules, the skill and the family files together, so this does not attribute its effect to any one of them.
  • Continuation is generic. It would help any OpenCode setup that hits output-limit stops, so present it as harness engineering rather than security expertise.
